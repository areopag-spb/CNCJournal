# ТЗ: доработка чат-бота ДОЗОР (eLog → AiService)

Составлено 11.11.2026 по итогам аудита решения.
Файл лежит вне `AiService/docs`: та папка — корпус документов самого чат-бота.

## 1. Цель

1. Чат отвечает на вопросы об инструменте по данным Портала (сейчас — по выгрузке `docs/stock.csv`).
2. Чат уверенно пользуется инструкцией оператора: находит нужный раздел и отвечает по нему.
3. Чат сам подсказывает оператору по инструкции, когда в смене возникла ситуация, описанная в ней.
4. Меньше раундов модели на вопрос и меньше ответов «из головы».

## 2. Как устроено сейчас

| Что | Где |
|---|---|
| Клиент чата (окно, сбор снимка смены) | `eLog/Infrastructure/AiChatClient.cs`, `eLog/ViewModels/AiChatViewModel.cs` |
| Эндпоинты `POST /api/chat`, `/api/chat/stream` | `AiService/Controllers/ChatController.cs` |
| Агентский цикл и проверки ответа | `AiService/Services/ChatAgentService.cs` |
| Описания инструментов | `AiService/Services/ChatTools.cs` |
| Системный промпт | `AiService/prompts/chat_system.txt` |
| Склад (выгрузка CSV) | `AiService/Services/StockService.cs` |
| Документы | `AiService/Services/DocsService.cs`, `AiService/docs/instrukciya_operatora.md` |
| Статистика и проверка смены | `AiService/Services/OperatorStatsService.cs` |
| Тесты | `AiService.Tests/ChatTests.cs` |

Известные слабые места:

- Модель (`qwen3:14b`) получает 13 инструментов и промпт на 425 строк и сама решает, что вызвать. Ошибается часто.
- Ошибки ловят около 25 проверок-«поручней» в `ChatAgentService.RunCoreAsync` уже после ответа. Каждая стоит лишнего раунда модели, бюджет — два раунда на вопрос.
- Поиск по документам подстроковый, без приведения слов к основе: «простоя» не находит «простой».
- Промпт, описания инструментов и история диалога занимают почти весь контекст (16 384 токена). Переполнение в чате не отслеживается; при переполнении Ollama молча отбрасывает начало промпта.
- Сценарии проверки чата (`research/ai-chat/`) не входят в git.

## 3. Что нужно получить от владельца до начала

- Портал: адрес, описание API (или схема БД), способ авторизации, учётная запись только на чтение.
- Какие сведения об инструменте есть в Портале: остаток, место хранения, выдача, аналоги, ресурс.
- Кто видит подсказки по событиям (все операторы или пилотная группа).

Без первого пункта этап 3 не начинать.

## 4. Работы

### Этап 1. Основа: сценарии и интерфейс источника

1.1. Перенести `research/ai-chat/scenarios.json`, `adversarial.json`, `groundtruth.json`, `run_probe.py`, `run_adversarial.py` в репозиторий (например, `AiService.Tests/ChatScenarios/`). Обезличить ФИО операторов.

1.2. Зафиксировать исходный результат: три прогона всех цепочек на текущем промпте, итог (PASS/WARN/FAIL по ходам) записать в этот файл, раздел 7.

1.3. Завести интерфейс `IToolInventorySource`:

- `SearchAsync(query)` — позиции по обозначению или словам;
- `GetAsync(designation)` — остаток и место хранения одной позиции;
- `FindAnalogsAsync(designation)` — аналоги, если источник их знает.

Текущий `StockService` сделать первой реализацией. Выбор реализации — в конфиге (`Stock:Source` = `csv` | `portal`). Поведение чата на этом шаге не меняется.

1.4. Добавить в чат учёт токенов: `ChatAsync` уже возвращает `PromptTokens`, `CompletionTokens`, `DoneReason`. Писать их в лог запроса; при заполнении контекста больше чем на 95% — предупреждение в логе.

Готово, когда: тесты зелёные, сценарии запускаются одной командой, исходный результат записан.

### Этап 2. Маршрутизация и инструкция

2.1. **Определять тему вопроса кодом до вызова модели.** Предикаты уже есть в `ChatAgentService` и `WebSearchService`: `AsksAboutSelf`, `AsksAboutPastShifts`, `AsksAboutPeriod`, `AsksAboutDowntime`, `AsksAboutServiceWait`, `AsksAboutPay`, `AsksAboutProgramDocs`, `IsStockQuestion`, `IsCorrection`. Собрать их в один класс `ChatIntentRouter` с результатом «тема + обязательные инструменты».

2.2. **Обязательный инструмент вызывать сразу**, его результат класть в сообщение до первого раунда модели. Образец — `ChatController.AugmentGreetingAsync` (приветствие уже так работает). Модель отвечает по фактам, а не выбирает инструмент.

2.3. **По теме — свой набор из 2–4 инструментов.** Остальные в запрос к модели не передавать.

2.4. **Промпт разбить** на ядро (роль, тон, запреты, формат) и тематические блоки (смена, прошлое, статистика, простои, склад, инструкция). В системное сообщение попадает ядро и блок темы. Версию промпта считать по набору использованных блоков.

2.5. **Инструкция по разделам.** `DocsService` разбивает `instrukciya_operatora.md` по заголовкам. Завести таблицу «тема вопроса → раздел». При вопросе о работе программы раздел подставляется в контекст целиком, без `search_docs`/`read_doc`.

2.6. **Поиск с приведением к основе.** Для вопросов, не попавших в таблицу: простое усечение окончаний русских слов в `DocsService.Search` (или общий префикс от 4 букв, как в `WordsMatch`). Проверить на парах «простоя/простой», «наладки/наладка», «нормативов/норматив».

2.7. **Ответ со ссылкой на раздел.** В ответе по инструкции должно стоять название раздела; кодом проверять, что оно есть в подставленном тексте.

2.8. **Убрать поручни, ставшие ненужными.** Тематические («не вызвал склад», «не открыл инструкцию», «личный вопрос без инструмента», «прошлое без истории», «период без статистики») удаляются: инструмент уже вызван кодом. Общие проверки ответа остаются: числа и обозначения в ответе есть в результатах инструментов (`FindUnverifiedCounts`, `FindUnverifiedDesignations`), имена инструментов и файлов не утекли (`LeaksToolName`), блок результатов поиска не вставлен целиком (`StripSearchDump`).

Границы, которые нельзя нарушить:

- оператору доступна только его инструкция (`ChatAgentService.OperatorDocs`); регламент мастера, план и статус в ответы не попадают;
- склад не подменяется поиском в сети;
- о деньгах и о данных мастера чат не отвечает.

Готово, когда: на сценариях доля PASS не ниже исходной; среднее число раундов модели на вопрос снизилось (мерить по логам); для вопросов о смене, складе и инструкции ответ приходит за один раунд.

### Этап 3. Инструмент из Портала

3.1. Реализация `PortalToolInventorySource` по API из раздела 3. Только чтение. Адрес и ключ — в `appsettings.Production.json`, в репозитории пусто.

3.2. Имя инструмента для модели остаётся `stock_search`, формат ответа тот же. На это имя завязаны проверки и сценарии.

3.3. Ответ инструмента — текст до 1500 символов с явными строками: «найдено N, показано M», «точного совпадения нет», «источник: Портал, данные на <время>». Модель не отличает «нет на складе» от «не влезло в выдачу».

3.4. Точное обозначение важнее похожего: на запрос `CNMG120408` не отдавать `CNMG120404` как равноценный результат. Правила уже есть в `StockService` — перенести.

3.5. **Разбор обозначения пластины кодом.** Новый инструмент `decode_insert(designation)`: по ISO-коду вернуть форму, угол при вершине, задний угол, размер, толщину, радиус. Таблица углов уже есть в `ChatAgentService` (`TurnAngles`). Для кодов без угла по первой букве (APKT, APMT, AEMT, SPKT, SEKT) отвечать «угол по коду не определяется». После этого убрать из промпта правила про углы и раунд `RewriteAngleAsync`.

3.6. Сбой Портала не ломает чат: таймаут 5–10 с, при ошибке инструмент отвечает «данные по инструменту сейчас недоступны», цифры не выдумываются. Возврат на CSV — настройкой, не автоматически (чтобы оператор не получил устаревший остаток под видом свежего).

3.7. Тесты: заглушка источника в `AiService.Tests`; сценарии «есть ли X», «сколько осталось», «где лежит», «чем заменить», «нет такой позиции», «Портал недоступен».

Готово, когда: ответы о наличии совпадают с Порталом на контрольных позициях; при выключенном Портале чат отвечает честным отказом за время не больше таймаута.

### Этап 4. Подсказки по инструкции без вопроса

Подсказку вызывает правило на данных, а не решение модели. Модель в лучшем случае формулирует текст; на первом шаге текст шаблонный.

4.1. Эндпоинт `POST /api/chat/hints`: на входе тот же снимок смены (`ElogChatContext`), на выходе список подсказок `{id, text, section}`. Расчёт — как в `get_shift_review` (`OperatorStatsService`), формулы те же, что в отчёте мастера.

4.2. Первые правила, каждое привязано к разделу инструкции:

| Событие | Подсказка |
|---|---|
| При запуске детали в нормативе стоит прочерк | прочерк допустим только при несовпадении операции, станка или числа установок с техкартой; иначе норматив вносится |
| Начат простой с типом, требующим доп. информации («Отказ оборудования», «Поиск и получение инструмента») | что нужно указать |
| Наладка превысила норматив | напомнить про комментарий с причиной |
| К концу смены не отмечено больше 5% времени | сколько минут не отмечено и что проверит мастер |
| Запись без М/Л | что указать в наименовании и количестве |

Порог 5% и формулы берутся из кода отчёта мастера, не дублируются.

4.3. Клиент eLog запрашивает подсказки по событиям (запуск детали, начало и конец простоя, завершение наладки, завершение смены), а не по таймеру. Показ — в окне чата или ненавязчивым уведомлением; оформление по `AGENTS.md` (палитра `Areopag.*`, без локальных цветов).

4.4. Не надоедать: одна подсказка на событие, без повторов по той же записи, кнопка «понятно». Подсказка ничего не блокирует.

4.5. Писать в лог: какое правило сработало, показана ли подсказка, изменил ли оператор запись после неё.

Готово, когда: на тестовых снимках смены каждое правило срабатывает и не срабатывает там, где не должно; подсказка не появляется дважды по одной записи.

## 5. Общие требования

- Правила проекта — `AGENTS.md`. Изменения в `libeLog` касаются и eLog, и remeLog.
- Очередь к модели общая с суточным анализом и подсказками мастеру (`OllamaService`). Каждый убранный раунд чата ускоряет и их.
- Любая правка промпта меняет его версию; версия пишется в ответ и в лог запроса.
- Сервис читает БД только на чтение; строка подключения — только в прод-конфиге.
- Данные в таблицах не правятся: только код, конфиг, промпт.
- Перед выкладкой: `dotnet test AiService.Tests`, три прогона сценариев, сравнение с исходным результатом.
- Прод — служба в `C:\AiService`; промпты туда сами попадают из репозитория при деплое владельцем.

## 6. Как мерить результат

| Показатель | Откуда | Ожидание |
|---|---|---|
| Доля PASS на сценариях (три прогона) | раннер сценариев | не ниже исходной, цель — выше |
| Раундов модели на вопрос | лог запросов чата | меньше исходного |
| Время ответа, медиана | лог запросов чата | меньше исходного |
| Сработавших поручней на вопрос | лог сервиса | меньше исходного |
| Доля суток с вопросами к отчёту мастера | `request_logs` суточного анализа | снижается после этапа 4 |
| Записи «нет норм» при причине «Другое» | `request_logs` подсказок мастеру | снижается после этапа 4 |
